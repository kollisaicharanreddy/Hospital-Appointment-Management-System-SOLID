Java testing guide (simple, beginner-friendly)

Overview
- This project uses JUnit 5 for unit tests and Maven to run the tests.
- Tests are in `src/test/java/` and are run with the Maven Surefire plugin when you run `mvn test`.
- Code coverage is produced with JaCoCo and the report is generated by `mvn test jacoco:report`.

Tools and files
- `JUnit 5` — the testing framework. Test methods are marked with `@Test`.
- `Maven` — build tool; `mvn test` compiles and runs tests.
- `JaCoCo` — coverage tool; `mvn jacoco:report` creates an HTML report at `target/site/jacoco/index.html`.
- Test locations: `src/test/java/` (three main test files in this project).

How tests are structured (simple view)
- A test file is a regular Java class. Each test method checks one small behavior.
- Arrange: create objects and prepare data (for example, add a patient to the in-memory store).
- Act: call the method under test (for example, book an appointment).
- Assert: check the result using assertions like `assertEquals`, `assertTrue`, `assertNull`, or `assertInstanceOf`.

Common patterns in our tests
- Nested groups: `@Nested` groups related tests inside the same file for readability.
- Test doubles: small helper classes (recording stubs) are used instead of complex mocking frameworks. They record how many times they were called and with what arguments.
- Capturing output: some tests capture `System.out` or provide fake `System.in` data to test the console `Main` program.
- Independence: each test creates its own `HospitalStore` so tests do not share state.

Running tests (commands)
```powershell
mvn test
mvn test jacoco:report
```

Deep dives: the three test files

1) `MainTest.java`
- Purpose: run the whole console program (`Main.main`) with a simulated user input stream and verify the printed output.
- Key techniques used:
  - Fake user input: `System.setIn(new ByteArrayInputStream(...))` supplies the menu choices and data the program expects.
  - Capture output: `System.setOut(new PrintStream(buffer))` collects the printed output for inspection.
  - Assertions: the test checks that the expected lines (like `added:Patient{1;Mina;100}`) appear in the output.
- Execution flow inside the test:
  1. Build a single String that contains the sequence of menu inputs, each separated by a newline.
  2. Replace `System.in` with that string as a byte stream.
  3. Replace `System.out` with a buffer to capture printed text.
  4. Call `Main.main(new String[0])` — the program reads inputs and runs the menu loop.
  5. Restore `System.in` and `System.out`.
  6. Check the captured output for expected messages.

2) `ServicesAndWorkflowTest.java`
- Purpose: unit-test the services and the in-memory `HospitalStore` behavior. These are focused, small tests that call service methods directly.
- Key techniques used:
  - Test doubles: `RecordingNotificationService`, `RecordingAllocationStrategy`, and `RecordingBillingService` are tiny classes used to verify interactions (calls and arguments) instead of real external systems.
  - Direct assertions: check returned objects, side effects on `HospitalStore`, and call counts on recording doubles.
- Execution flow inside tests:
  1. Create a fresh `HospitalStore` and any required test doubles.
  2. Construct the service under test (e.g., `AppointmentBookingService`) and pass the doubles or store to it.
  3. Call the method under test (`book`, `cancel`, `reschedule`, `generate`, etc.).
  4. Assert expected outcomes: return values, changed store state, and that the doubles were called with correct values.

3) `tests/FactoriesAndPureComponentsTest.java`
- Purpose: test pure components such as factories, allocation strategies, notification implementations, billing policies, report generators, and simple model `toString()` methods.
- Key techniques used:
  - `assertInstanceOf` to confirm factories return the correct concrete types.
  - Using small `HospitalStore` setups to validate strategy behavior (for example, the specialty-based allocation returns the matching doctor id).
  - Capturing `System.out` to test notification implementations print the expected message formats.
  - For model tests, instantiate models and assert fields and `toString()`.
- Execution flow inside tests:
  1. For factory or strategy tests: create a `HospitalStore` when needed, call the factory or strategy, and assert the returned object type or behavior.
  2. For notification tests: capture `System.out`, call the notification method, and check the captured string contains the expected prefix and text.
  3. For model tests: instantiate the model (like `Patient` or `Doctor`) and assert fields and `toString()` output.

Tips to read the tests (if you are new)
- Start with `ServicesAndWorkflowTest.java` to see how small service methods behave.
- Read `FactoriesAndPureComponentsTest.java` to understand how simple pieces are verified in isolation.
- Finally, open `MainTest.java` to see how the full program is exercised using simulated user input.
